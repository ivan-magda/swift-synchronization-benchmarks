swiftlang-6.4.0.34.1, XcodeGen 2.46.0, Release `-O`, whole-module

I inspected the complete disassembly, specialized loop bodies, async resume

objdump listing can label imported stubs with a misleading nearest symbol.
Raw listings remain in ignored `build/private/acceptance/`.

```bash
APP=build/artifacts/<buildID>/SyncBench.app/SyncBench
xcrun nm "$APP" | xcrun swift-demangle
xcrun llvm-objdump --no-show-raw-insn --disassemble "$APP"
xcrun llvm-objdump --macho --indirect-symbols "$APP"
xcrun llvm-objdump --no-show-raw-insn \
  --disassemble-symbols='<mangled-symbol-from-nm>' "$APP"
```

## Loop coverage and compiler merging

Each target contains 49 top-level specialized loop bodies, 17 async resume
bodies, and 6 async function-pointer records: 72 `BaseComparisonLoops` symbols.
The compiler represents the 60 logical mechanism/operation combinations with
43 synchronous bodies and 6 async entries. It merges 11 logical synchronous
loops. Therefore 60 separate loop symbols do **not** exist.

The following table covers read, write, and increment for all 20 families in
both targets. The iOS 18 runtime plan selects only Mutex and the four atomic
rows; the executable still contains the other families.

| Mechanism | Optimized paths in both targets |
| --- | --- |
| unsynchronized | Separate read/write/increment bodies; reductions described below |
| mutex | Three bodies; direct unfair-lock lock/unlock calls |
| osAllocatedUnfairLock | Three bodies; direct unfair-lock lock/unlock calls |
| osAllocatedUnfairLockAdaptiveSpin | Three bodies; flags translation and adaptive-spin acquisition |
| osUnfairLock | Three bodies; direct unfair-lock lock/unlock calls |
| nsLock | Three shared Objective-C message-send bodies with NSRecursiveLock |
| nsRecursiveLock | Same three bodies as NSLock; forwarding thunk preserves receiver |
| pthreadMutex | Three shared bodies with ObjC monitor and pthread reader-writer lock |
| pthreadReadWriteLock | Shared bodies receive distinct read-lock/write-lock/unlock pointers |
| objcSync | Shared bodies receive objc_sync_enter/objc_sync_exit pointers |
| serialQueue | Read shares the queue-read body; write/increment call queue.sync |
| barrierQueueSyncWrite | Read shares the queue-read body; write/increment call sync with barrier |
| barrierQueueAsyncWrite | Read shares the queue-read body; write/increment submit barrier blocks |
| dispatchSemaphore | Three bodies; semaphore wait/signal calls |
| actor | Three async entries plus resume functions; executor hops and inlined state access |
| mainActor | Three async entries plus resume functions; MainActor executor acquisition/hops |
| atomic | Three bodies; inline loads/stores/RMW instructions |

| managedAtomicRelaxed | Three bodies; storage accessor call followed by relaxed atomic instruction |

The ObjC/pthread group reduces nine bodies to three, the NSLock group reduces
six to three, and the queue-read group reduces three to one. I followed the
forwarding thunks and their function-pointer arguments for each merged family.
I left these compiler choices intact and added no calls to inhibit optimization.

## Locks, allocation, and exclusivity

All three Mutex bodies call `os_unfair_lock_lock` and
`os_unfair_lock_unlock` directly around the integer access. For example, the
iOS 26 increment body at `0x100008acc` calls their stubs at `0x100037d60`
and `0x100037d78`. The iOS 18 increment body starts at `0x100008b0c` and
uses the same APIs. Allocated and raw unfair-lock rows have the same direct
acquisition/release pattern. Adaptive spin calls
`os_unfair_lock_lock_with_flags`, with translated flags and the library's
ordinary-lock fallback path.

The synchronous lock-loop bodies contain no direct `swift_allocObject`,
`swift_retain`, or `swift_release` calls. This statement describes the visible
loop and wrapper code; imported Foundation/libdispatch implementations retain
their own runtime behavior. Semaphore rows call wait/signal without direct Swift
allocation or ARC calls in the loop.

Async barrier write/increment bodies call `swift_allocObject`, block copy/release,
and Swift retain/release for submitted closures. These allocations belong to
the queued-write mechanism. MainActor resume paths release executor references.
I did not classify either as a harness allocation in a lock row.

The queue-state capture helpers call `swift_beginAccess`: the merged serial-queue
exclusive helper, the concurrent queue shared-read helper, and the async barrier
write helper. Merged queue thunks route the corresponding operations to these
helpers. ManagedAtomic loops call its storage accessor through a function
pointer; the accessor also calls `swift_beginAccess`/`swift_endAccess`.
The specialized plain-lock, unsynchronized, and inline Atomic bodies have no
`swift_beginAccess` calls. Harness barriers and result encoding also contain
access checks outside these measured operation loops.

## Atomic instructions

| Operation | ios26 | ios18 |
| --- | --- | --- |
| Atomic and ManagedAtomic increment, acquiring/releasing | `ldaddal` | retry loop with `ldaxr` / `stlxr` |
| Relaxed Atomic and ManagedAtomic increment | `ldadd` | retry loop with `ldxr` / `stxr` |
| Acquiring read | `ldapr` | `ldar` |
| Releasing write | `stlr` | `stlr` |
| Relaxed read/write | `ldr` / `str` | `ldr` / `str` |

The two increment patterns match the intended deployment-target comparison.
The iOS 26 Atomic increment starts at `0x100008410`; its `ldaddal` is at
`0x100008420`. The relaxed body uses `ldadd` at `0x1000083fc`.
The iOS 18 Atomic body starts at `0x100008440`, with `ldaxr` at
`0x100008454` and `stlxr` at `0x10000845c`. Its relaxed counterpart uses
`ldxr`/`stxr` at `0x100008420`/`0x100008428`.

## Unsynchronized floor

The compiler hoists the read's memory load out of the loop, retains checked
addition/overflow paths, unrolls them, and computes the result with a multiply.
The write body retains overflow checks for the value sequence, removes
intermediate stores, and stores the last value once. Increment collapses to a
single load, addition of `count`, and store. Both targets have these reductions.
The floor therefore measures optimized single-thread code, and cannot establish
the cost of a repeated ordinary memory access. The contention variants exclude it.
